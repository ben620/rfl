## 测试方法

基准程序位于 `benchmarks/json_benchmark.cpp`，构建目标为 `rfl_benchmarks`。

- 每个用例先预热 `iterations / 10 + 1` 次
- 正式测量 3 轮，**取最优值**，轮次之间休眠 2 ms 以降低热降频影响
- 通过重载全局 `operator new` 统计堆分配次数与字节数
- 使用 `volatile` 汇聚变量防止结果被优化消除
- 支持按名称过滤：`rfl_benchmarks.exe <关键字>`

运行方式：

```
cmake -S . -B build
cmake --build build --config Release
build\Release\rfl_benchmarks.exe
```

## 优化项清单

### 输出层（参考 `std::format` 的连续缓冲设计）

| 优化 | 说明 |
|---|---|
| 本地栈缓冲 | `ToJson` 默认先写入 256 字节栈缓冲 |
| 几何扩容 | 溢出后按约 1.5 倍增长 |
| 复用容量 | 新增 `ToJson(value, std::string&)` |
| 长度预计算 | 新增 `JsonSize(value)`，等价 `formatted_size` |
| 单字符快速路径 | `{`、`}`、`,`、`:` 直写缓冲 |
| 字面量重载 | `append(const char(&)[N])` 免去 `strlen` |
| 去除清零 | 数字缓冲与 4 KiB sink 缓冲不再值初始化 |

### 数字与字符串

| 优化 | 说明 |
|---|---|
| `std::to_chars` | 无 locale、无临时字符串 |
| 最短浮点格式 | `0.1` 输出 `0.1` 而非 `0.10000000000000001` |
| 转义快速路径 | 普通字节仅做紧凑判断，按连续区段批量复制 |
| 字段名免扫描 | 反射字段名是合法标识符，无需转义检查 |

### 反射遍历

| 优化 | 说明 |
|---|---|
| 单次 tie | 消除每字段重建引用 tuple 的 \(O(N^2)\) 行为 |
| 短路遍历 | 新增 `for_each_member_while`，`&&` fold 真正提前退出 |
| 编译期逗号 | 由字段索引在编译期决定，去掉运行时 `first` 标志 |

### 反序列化

| 优化 | 说明 |
|---|---|
| 视图化字符串 | 无转义时直接 `assign` 视图，不逐段解码 |
| 键名零分配 | `parse_key` 返回 `string_view` |
| 语法级跳过 | 未知字段只验证语法，不解码不分配 |
| 长度预筛 | 字段匹配先比长度再比内容 |
| 匹配短路 | 命中字段后立即停止遍历 |
| 原地构造 | `emplace_back` 后直接解析，省掉一次移动 |

### 网络输出

| 优化 | 说明 |
|---|---|
| 分块聚合 | 默认聚合到 4096 字节再调用 sink，减少系统调用 |
| 大块直通 | 超过缓冲的数据直接发送，省一次 `memcpy` |
| 部分写入 | sink 可返回消费字节数，自动重试剩余部分 |

## 尝试后回退的优化

**`vector` 容量启发式 `reserve`**

按剩余输入长度估算元素数量并预留容量。实测导致过度分配与堆碎片：

| 用例 | 无 reserve | 带 reserve | 结果 |
|---|---|---|---|
| Track(嵌套 5k) | 477.5 μs | 1759.8 μs | 慢 3.7× |
| Message(64K) | 29.4 μs | 156.6 μs | 慢 5.3× |

虽然 `vector<int>[10k]` 的分配从 24 次降到 1 次，但整体明显退化，因此回退，仅保留 `emplace_back`。

## 遗留问题修复（第二轮）

### 1. 反序列化失败会部分修改目标对象（已修复）

原实现边解析边写入目标，失败时对象可能已被部分改写，`vector` 还会在开头被清空。

修复方式：

- `FromJson(input, value)` 改为**事务语义**：先解析到临时对象，成功后再 `std::move` 提交
- 新增 `FromJsonInPlace(input, value)`：直接写入目标，可复用已有容器容量，但失败时目标可能被部分修改

```cpp
User user;                                  // 失败时保持不变
rfl::FromJson(json, user);

std::vector<int> data;                      // 复用容量，失败时可能部分修改
rfl::FromJsonInPlace(json, data);
```

### 2. 字符串不校验 UTF-8（已修复）

原实现把高位字节原样输出，孤立续字节、过长编码、代理项和超范围码点都会生成非法 JSON。

修复方式：

- 新增 `utf8_sequence_length` 校验多字节序列（长度、续字节、最小码点、代理项、上限 0x10FFFF）
- 序列化与反序列化共用同一套校验
- 遇到非法序列时：序列化返回失败（`ToJson(value)` 抛 `std::domain_error`），解析返回 `false`

### 3. `span` 输出与输入重叠时为 UB（已修复语义）

`span_writer` 的复制已确认使用 `memcpy`，其语义要求源与目标区间不重叠。

修复方式：在 `span_writer` 上明确写出前置条件，并在文档中说明：

> `output` 不得与序列化值或其嵌套字符串的存储重叠

这与 `std::string::append`、`std::ranges::copy` 等标准接口的要求一致。真正支持原地输出需要两阶段方案，与无动态分配目标冲突，暂不提供。

### 4. 模板实例化膨胀（已修复）

原 `buffered_sink_writer<BufferSize, Sink>` 让每个 lambda 类型与每个 `BufferSize` 都完整实例化整个 `write_json` 核心。

修复方式：

- 引入类型擦除的 `sink_ref`（`void*` 上下文 + 函数指针），归一化 `void`/`bool`/整数三种 sink 返回类型
- `buffered_sink_writer` 改为非模板类，缓冲区由调用方以 `span<char>` 传入
- 序列化核心现在只按值类型实例化一次

修复过程中发现并修复了一个严重缺陷：`sink_ref` 的转发构造函数劫持了拷贝构造，导致内部 `context_` 指向已销毁的构造函数参数。表现为 Release 下访问违例、Debug 下正常。修复方式是排除自身类型并显式提供拷贝/赋值。

### 5. 修复带来的额外优化

为抵消 UTF-8 校验的开销，引入字节分类查表 `byte_class`：

- `0`：普通 ASCII，直接复制
- `1`：需要转义（控制字符、引号、反斜杠）
- `2`：多字节 UTF-8 起始字节，需要校验

序列化转义与解析扫描共用该表，把多次条件判断压缩为一次索引比较。

## 当前遗留问题

以下问题尚未处理：

- 解析失败时的错误位置语义不完全一致：数字语法错误会回滚到开头，而 `from_chars` 溢出/类型不匹配则停在数字末尾
- 输出 JSON 的深度嵌套递归没有上限（解析器已限制 128 层，序列化器未限制）
- `vector<bool>` 的代理引用类型不受序列化支持
- 浮点输出缓冲固定 128 字节，对标准允许的非典型浮点实现未做静态约束
- 若未来支持自定义字段别名，别名可能包含需转义字符，届时字段名免转义快速路径需要区分处理

## 测量注意事项

- 本机为笔记本平台，长时间高负载会触发降频。基准已下调大用例迭代次数以缩短总时长
- 若单次运行结果异常偏慢，建议先让 CPU 冷却，或使用过滤参数单独测量
- 吞吐按 JSON 字节数除以耗时计算，小对象的吞吐值受固定开销影响较大，横向比较应以 ns/op 为主

### 关于第一轮基线数据的可靠性

第一轮的基线在大用例上采用较高迭代次数（2000 / 1000 / 500000），单次运行时间较长，后期用例可能已受到降频影响。因此第一轮表格中**大用例的"优化前"数值偏慢**，对应提升倍数（如 `Track`、`Message(64K)`）被高估。

第二轮已将大用例迭代次数下调（100 / 200）并在轮次间休眠，数据在同一次运行中前后一致。对比两轮大用例结论时应以第二轮数据为准；小对象（ns 级）数据受此影响很小，仍然可靠。

### 关于 `keep` 与容器复用

反序列化基准使用外部声明的输出容器并调用 `FromJsonInPlace`，以真实反映容量复用路径。使用事务性的 `FromJson` 会额外构造临时对象并丢弃复用容量，测得的数值会偏高。
